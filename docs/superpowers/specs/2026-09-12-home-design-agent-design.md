# 户型效果预览 Agent — 设计文档 (Spec)

- 日期：2026-09-12
- 状态：已通过头脑风暴，待评审
- 路线：**路线 B** — 识别 → 结构化方案(Scheme) → 双通道出图

---

## 1. 背景与目标

设计师/销售在量房或谈单**当场**，输入一张户型图和客户的装修需求，Agent 快速产出**效果预览**用于沟通谈单；客户选定方案后再生成 **3D 可漫游模型**。

- **使用者**：设计师 / 销售，**当场驱动**（非 C 端自助）。
- **硬指标**：快（单张预览尽量几十秒内）、能现场改、**图不能跑偏**（墙体/户型必须和客户家一致）。

### 输入
- **户型**：图片（JPG/PNG 截图）——需先做视觉识别。
- **需求**：**结构化选项框 + 口述** 组合。

### 输出（两阶段）
1. **快速预览**：彩平图 + 3~4 张关键视角实景图（当场展示、可迭代）。
2. **3D 可漫游模型**：客户选定方案后生成。

---

## 2. 总体架构

一条流水线，7 个职责单一的模块，中间贯穿一份**结构化方案 Scheme**（系统的中心资产）。

```
用户输入(户型图 + 需求)
      │
      ▼
① 户型识别 FloorPlan Parser   视觉模型 → FloorPlan(房间/尺寸/门窗/承重墙/朝向)
      ▼
② 需求解析 Requirement Parser LLM → Requirement(风格/预算/人口/硬约束/偏好)
      ▼
③ 方案生成 Scheme Generator ★ LLM → Scheme(逐房间布局/家具/材质/软装 + render_prompt)
      │  (唯一决策中心；客户改动只回到这里、只重跑对应房间)
      ├───────────────┬──────────────────────────┐
      ▼               ▼                            ▼
④ 彩平图渲染(2D)   ⑤ 实景图生成(透视)         ⑥ 3D场景&漫游(阶段二)
  程序化SVG,零AI     商业图像API+构图参考         Scheme实例化→Three.js
  保「准」           保「美」                     保「沉浸」
      └──────┬────────┘
             ▼
      快速预览(彩平图 + 实景图) → 设计师展示 → 客户挑/改 → 回③迭代

⑦ 存储 & 案例库：生产整包落库；索引键 = 小区 + 户型 + 风格
   - 历史预览：随时调出过往成品
   - 同小区/同户型参考：给客户看「别人家怎么装的」（纯展示，不复用）
```

### 两个架构要点
1. **③是唯一决策中心**：所有"设计判断"集中在③，④⑤⑥只是把 Scheme 翻译成不同表现形式（2D/实景/3D），保证三种输出说的是同一套方案。
2. **迭代回路在③**：客户改动 = 改 Scheme 局部 + 重跑对应房间的④⑤，不重算全屋。改动可追踪、可撤销。

---

## 3. 核心数据结构：Scheme

Scheme 由③生成、④⑤⑥消费。要求：结构化到能直接翻译成图和 3D；房间为独立单元，可局部修改。

```jsonc
{
  "scheme_id": "...",
  "floorplan_ref": "...",
  "global": {
    "style": "北欧",
    "palette": ["米白", "浅木", "雾蓝"],
    "budget_level": "中",
    "materials": { "地面": "浅色木地板", "墙面": "乳胶漆-米白" }
  },
  "rooms": [
    {
      "room_id": "living_room",
      "name": "客厅",
      "area": 22.5,
      "layout": [
        { "item": "布艺三人沙发", "pos": [x,y], "facing": "北", "size": [2.4,0.9] },
        { "item": "电视柜", "pos": [x,y], "facing": "南" }
      ],
      "finishes": { "地面": "...", "墙面": "...", "吊顶": "..." },
      "soft": ["落地灯", "地毯-几何纹", "绿植"],
      "render_prompt": "..."   // 由本房间结构自动生成的实景图提示词
    }
  ],
  "constraints_check": [
    { "rule": "不拆承重墙", "status": "pass" },
    { "rule": "餐厅容纳6人餐桌", "status": "pass" }
  ]
}
```

### 三个设计要点
1. **房间是独立单元**：客户"只改客厅"→ 只重生成 `living_room` + 重渲其图。当场快速迭代的关键。
2. **`render_prompt` 内嵌每房**：③生成方案时顺手写好实景图提示词，⑤直接取用，保证图与方案一致。
3. **`constraints_check` 显式落库**：硬约束校验结果写进 Scheme，拦住"AI 拆了承重墙"这类事故。

## 4. 模块技术细节与难点

### ① 户型识别 (FloorPlan Parser) — 地基，最易翻车
- **做法**：多模态视觉模型（GPT-4o / Gemini / Qwen-VL）读图 → FloorPlan JSON。
- **难点**：户型图千奇百怪，视觉模型读**精确尺寸/坐标易不准**。
- **破法**：(a) **人在环校验**——识别结果叠原图给设计师确认/微调（拖框、改面积），把地基锁死；(b) 优先保证**拓扑正确**（几室几厅、相邻关系、门窗位置），精确坐标次要，够摆家具即可。

### ② 需求解析 (Requirement Parser) — 最简单
- **做法**：选项框结构化直接用；口述用 LLM 抽成结构化字段；**冲突以选项框为准**，口述补充。
- **难点**：口述里的硬约束（"老人房必须一楼"）须可靠抽出 → `constraints`。
- **破法**：专门跑一遍"硬约束提取"子任务，宁可多抽。

### ③ 方案生成 (Scheme Generator) — 系统大脑 ★
- **做法**：LLM 拿 FloorPlan + Requirement 生成完整 Scheme。
- **难点**：(a) 家具摆位要合理（沙发不挡门、床不贴马桶墙）；(b) 必须过硬约束。
- **破法**：(a) **LLM 决策 + 规则兜底**——LLM 定"放什么、大致哪面墙"，轻量规则层做碰撞检测/门窗避让并摆干净坐标；(b) 生成后立即跑 `constraints_check`，不过则**自动重试**该项，通过才落库。

### ④ 彩平图渲染 (2D Colored Plan) — 纯工程、零 AI、绝对可控
- **做法**：从 Scheme 坐标**程序化画图**（SVG/Canvas 或 headless 渲染），墙/家具按数据画 + 材质贴图/图例。
- **价值**：墙体**绝不跑偏**、天生可编辑（改数据=改图）。「图不跑偏」的定海神针。

### ⑤ 实景图生成 (Perspective Render) — 好看那一层
- **做法**：调商业图像 API，输入 = 每房 `render_prompt` + **构图参考图**（④彩平图/户型轮廓做空间约束）+ 风格参考图；每房 1~2 关键视角。
- **难点**：商业 API 空间一致性有限，可能改布局。
- **破法**：(a) "参考图 + 精准提示词"双重约束压小偏差；(b) 分工明确——**彩平图负责准、实景图负责美**；(c) 封装为可替换接口，后续无缝换自建 SD+ControlNet。

### ⑥ 3D 场景构建 & 漫游 (阶段二) — 客户选定后才做
- **做法**：选定 Scheme **实例化成 3D**——从家具模型库按 `item` 取模型、按坐标摆放、套材质，Web3D（Three.js 或对接第三方家装 3D 引擎）出可旋转/漫游场景。
- **难点**：需要**家具 3D 模型库**（`item` → 模型）。
- **破法**：先建常用家具小模型库 + 兜底占位模型，逐步扩充；或直接对接成熟第三方 3D 家装引擎 API。

### ⑦ 存储 & 案例库 — 纯参考展示
- **存**：每次生产整包（户型图/FloorPlan/需求/Scheme/彩平图/实景图/3D）。
- **检索**：`小区 + 户型(房型/面积) + 风格` 索引。
- **能力**：历史预览；同小区/同户型参考（给客户看别人家怎么装，**纯展示，不复用为起点**）。
- **技术**：PostgreSQL（结构化 + JSONB 存 Scheme）+ 对象存储（图片/模型）。

## 5. 技术栈

| 层 | 选型 |
| --- | --- |
| 后端/编排 | Python + FastAPI，轻量有向流水线（六步串联，不上重框架） |
| 视觉识别① | 多模态 API（GPT-4o / Gemini / Qwen-VL） |
| 解析②③ | LLM |
| 图像⑤ | 商业图像 API（即梦/豆包/Gemini Image），封装为可替换接口 |
| 彩平图④ | 服务端 SVG/Canvas 渲染 |
| 3D⑥ | Web 端 Three.js 或第三方家装 3D 引擎 |
| 存储⑦ | PostgreSQL(JSONB) + 对象存储 |
| 前端 | 设计师 Web 工作台（上传→确认识别→看方案→改→展示） |

## 6. 错误兜底

- **两个人在环卡点**：①识别后设计师确认；③约束不过自动重试并高亮——把翻车挡在出图前。
- **按房间幂等**：任何一步失败或要改，只重跑那一间/那一步，不重来全屋。
- **识别缓存**：同一张户型图只识别一次，反复出方案不重复付费。

---

## 7. 测试策略

- **①识别**：标注过的户型图测试集，测"拓扑准确率"（几室几厅/相邻关系/门窗）作回归基线。
- **③方案**：约束校验必须 100% pass 才通过 + 几个"黄金户型"人工评审布局合理性。
- **⑤实景图**：难自动化，用评分量表人工抽检（风格符合度/空间一致性/美观度）。
- **端到端**：几个样板户型跑冒烟，确保链路不断。

---

## 8. 分期落地

- **Phase 0 — MVP（验证当场出预览）**：①(带人工校验) + ② + ③ + ④彩平图 + ⑤实景图。单户型跑通，**暂不做 3D、不做案例库**。此版即可让设计师当场出预览谈单。**价值验证点，也是后续所有阶段的地基。**
- **Phase 1**：⑦存储 + 案例库（历史预览 + 同小区参考）。
- **Phase 2**：⑥ 3D 可漫游。
- **Phase 3**：自建 SD+ControlNet 替换⑤，一致性与风格再上台阶。
